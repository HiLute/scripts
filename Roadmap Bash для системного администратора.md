# Roadmap: Bash для системного администратора

Oct 7, 2026 · @Максим

## Как пользоваться

Восемь этапов, примерно 8–9 недель при 1–1,5 часах в день. Каждый этап заканчивается скриптами, которые остаются в твоём репозитории.

Командная строка, пайпы и редиректы, права, процессы, systemd, сеть и git у тебя уже есть, поэтому roadmap начинается сразу со скриптов.

**Окружение**

- Скрипты пиши в nvim, запускай на VM из лабы (Ubuntu Server, Debian 13, Rocky Linux). Скрипты с `sudo` и `rm` безопаснее ломать там, чем на основной системе.
- Заведи репозиторий `scripts` на GitHub: один этап — одна папка, каждый рабочий скрипт — отдельный коммит.
- Поставь `shellcheck` и `shfmt` с первого дня и прогоняй через них каждый скрипт.
- Пиши именно на Bash, с первой строкой `#!/usr/bin/env bash`, даже если в терминале у тебя zsh: на серверах по умолчанию будет Bash.

**Этапы**

| № | Этап | Что остаётся на выходе | Срок |
| --- | --- | --- | --- |
| 1 | Анатомия скрипта | Три коротких скрипта с переменными и кодами возврата | 3–4 дня |
| 2 | Условия и циклы | Проверки служб и дисков, работающие на всех VM | 1 неделя |
| 3 | Аргументы, ввод и вывод | Утилита с флагами и справкой | 1 неделя |
| 4 | Функции и структура | Свой шаблон скрипта | 1 неделя |
| 5 | Текст и данные | Разбор логов и конфигов | 1–1,5 недели |
| 6 | Надёжность и отладка | Скрипты проходят shellcheck, пишут лог, не запускаются дважды | 1 неделя |
| 7 | Автоматизация | Бэкап по таймеру, обход хостов по SSH | 1,5 недели |
| 8 | Итоговые проекты | 2–3 проекта с README на GitHub | 1–2 недели |

Сроки — ориентир. Критерий перехода к следующему этапу один: практика этапа сделана и строка «Готов, когда» выполняется.

## Этап 1. Анатомия скрипта

Цель этапа — писать и запускать скрипты, не путаясь в кавычках: на них приходится большая часть ошибок в начале.

**Темы**

- Shebang `#!/usr/bin/env bash`, `chmod +x`, запуск через `./script.sh`, `bash script.sh` и `source` — в чём разница
- Переменные: присваивание без пробелов, `$var` и `${var}`, переменные окружения и `export`
- Кавычки: двойные, одинарные и их отсутствие; word splitting и globbing
- Подстановка команд `$(...)` и арифметика `$(( ))`
- Коды возврата: `$?`, `exit`, цепочки через `&&` и `||`
- Специальные переменные: `$0`, `$1`…`$9`, `$#`, `$@`, `$$`

**Практика**

- [x] `sysinfo.sh`: выводит hostname, версию ОС из `/etc/os-release`, аптайм и занятое место на `/`
- [ ] `mkproject.sh <имя>`: создаёт папку проекта с подпапками и README; без аргумента завершается с ошибкой и ненулевым кодом
- [ ] Сломать любой свой скрипт файлом с пробелом в имени и починить кавычками

**Готов, когда** объясняешь, чем `"$@"` отличается от `$*` и почему `"$var"` почти всегда пишут в кавычках.

## Этап 2. Условия и циклы

После этапа скрипт принимает решения и обходит наборы файлов, служб и хостов.

**Темы**

- `if / elif / else`; `[[ ]]` против `[ ]` и `test`
- Проверки файлов (`-f`, `-d`, `-r`, `-x`), строк (`-z`, `-n`, `==`, `=~`) и чисел (`-eq`, `-lt`, `(( ))`)
- `case` с шаблонами
- `for` по списку, по glob и в стиле C; `while` и `until`; `break` и `continue`
- Чтение файла построчно: `while IFS= read -r line; do ...; done < file`
- Почему нельзя разбирать вывод `ls` и чем его заменить: glob и `find`

**Практика**

- [ ] `check-services.sh`: проходит по списку служб и печатает те, что не active (`systemctl is-active`)
- [ ] `disk-alert.sh`: предупреждает, если раздел заполнен больше заданного процента
- [ ] `rename-logs.sh`: добавляет дату в имена всех `*.log` в каталоге
- [ ] `os-detect.sh`: через `case` определяет Debian, Ubuntu или Rocky по `/etc/os-release` и печатает нужный пакетный менеджер

**Готов, когда** один и тот же скрипт без правок отрабатывает на всех трёх VM.

## Этап 3. Аргументы, ввод и вывод

Скрипт превращается в утилиту: с флагами, справкой и раздельными потоками для результата и ошибок.

**Темы**

- Позиционные параметры, `shift`, значения по умолчанию `${1:-default}`
- `getopts` для коротких флагов; ручной разбор длинных через `while` и `case`
- `read`: приглашение `-p`, скрытый ввод `-s`, таймаут `-t`
- Потоки: stdout и stderr, `>&2`, `2>&1`, `&>`, `/dev/null`, `tee`
- Here-document и here-string: `<<EOF` и `<<<`
- `printf` вместо `echo` для форматированного вывода
- Код возврата конвейера: `PIPESTATUS` и `set -o pipefail`

**Практика**

- [ ] Добавить в `disk-alert.sh` флаги `-t <порог>`, `-q` (тихий режим) и `-h` (справка)
- [ ] `adduser-batch.sh <файл>`: создаёт пользователей по списку из файла, ошибки пишет в stderr
- [ ] Функция подтверждения: скрипт спрашивает «Точно удалить? \[y/N\]» перед опасным действием

**Готов, когда** `script.sh -h` печатает справку, а при `script.sh > out.txt` ошибки остаются на экране и не попадают в файл.

## Этап 4. Функции и структура скрипта

Итог этапа — собственный шаблон, с которого начинается каждый следующий скрипт.

**Темы**

- Функции: объявление, аргументы, `local`, `return` против `exit`, возврат значения через stdout
- Структура файла: константы наверху, затем функции, внизу `main "$@"`
- Strict mode `set -euo pipefail`: что делает каждая опция и в каких случаях `-e` подводит
- `trap`: уборка на `EXIT`, обработка `INT`, `TERM` и `ERR`
- `mktemp` для временных файлов и каталогов
- Общий код в отдельном файле `lib.sh`, подключение через `source`

**Практика**

- [ ] `template.sh`: strict mode, функции `log`, `die`, `usage`, `cleanup` через `trap`, точка входа `main`
- [ ] Переписать `check-services.sh` и `disk-alert.sh` на шаблон
- [ ] Вынести `log` и `die` в `lib.sh` и подключить из двух скриптов

**Готов, когда** при Ctrl+C посреди работы скрипт убирает за собой временные файлы.

## Этап 5. Текст и данные

Большая часть админских скриптов — это разбор текста: логов, конфигов и вывода других команд.

**Темы**

- Parameter expansion: `${var#prefix}`, `${var%suffix}`, `${var/old/new}`, `${#var}`, `${var^^}`, `${var:?сообщение}`
- Массивы: объявление, `"${arr[@]}"`, длина, добавление элементов, обход; `mapfile`
- Ассоциативные массивы: `declare -A`, счётчики по ключу
- Регулярные выражения: `grep -E`, `[[ =~ ]]` и `BASH_REMATCH`
- `sed`: замена, удаление строк, правка файла на месте через `-i`
- `awk`: поля, разделитель `-F`, условия, суммы и подсчёты
- Мелкие утилиты: `cut`, `sort`, `uniq -c`, `tr`, `wc`, `head`, `tail`, `xargs`
- `jq` для JSON

**Практика**

- [ ] `ssh-fails.sh`: топ-10 IP-адресов с неудачными входами по SSH из `journalctl`; учесть, что служба называется `ssh` на Debian и Ubuntu и `sshd` на Rocky
- [ ] `users-report.sh`: по `/etc/passwd` печатает таблицу «пользователь, UID, shell» для учёток с UID от 1000
- [ ] `conf-set.sh <файл> <ключ> <значение>`: меняет значение в конфиге вида `key=value` или дописывает строку, если ключа нет
- [ ] Разобрать вывод `ip -j addr` через `jq`: интерфейсы и их IPv4-адреса

**Готов, когда** на задачу «посчитать что-то в логе» сразу складывается цепочка из `grep`, `awk`, `sort` и `uniq`.

## Этап 6. Надёжность и отладка

Скрипт, который cron запускает в три часа ночи, должен сам объяснить в логе, что пошло не так.

**Темы**

- `shellcheck`: читать предупреждения и разбираться в причине, а не глушить их
- Отладка: `bash -x`, `set -x` на отдельном участке, `PS4` с номером строки
- Логирование: функция `log` с датой и уровнем, `logger` для записи в journald
- Защита от двойного запуска через `flock`
- Идемпотентность: повторный запуск ничего не ломает и не дублирует
- Проверки на входе: нужные команды (`command -v`), права root (`$EUID`), существование файлов
- Безопасность: не использовать `eval`, не оставлять `rm -rf "$dir/"` с возможной пустой переменной, не хранить секреты в коде и репозитории
- Стиль: Google Shell Style Guide, форматирование через `shfmt`

**Практика**

- [ ] Прогнать все прежние скрипты через `shellcheck` и исправить каждое замечание
- [ ] Добавить в шаблон запись в файл лога и в journald, проверку зависимостей и `flock`
- [ ] Написать скрипт с намеренной ошибкой и найти её через `bash -x`
- [ ] Режим `--dry-run` для `adduser-batch.sh`: печатает команды, но не выполняет их

**Готов, когда** `shellcheck` молчит на всём репозитории, а второй экземпляр запущенного скрипта отказывается стартовать.

## Этап 7. Автоматизация админских задач

Здесь Bash соединяется с тем, что ты уже знаешь: systemd, SSH, rsync и PostgreSQL.

**Темы**

- Планировщики: `cron` и `crontab`, systemd timers (пара `.service` и `.timer`), окружение и `PATH` под планировщиком
- Бэкапы: `tar`, `rsync`, ротация по количеству и возрасту (`find -mtime`), проверка архива
- Удалённое выполнение: `ssh host 'команда'`, цикл по списку хостов, `scp` и `rsync`, вход по ключам
- Службы и логи из скриптов: `systemctl`, `journalctl` с фильтрами
- Пользователи: `useradd`, `usermod`, `chage`, раскладка SSH-ключей
- Уведомления о сбоях: ненулевой код возврата, `OnFailure=` в unit-файле, отправка сообщения через `curl`

**Практика**

- [ ] `backup.sh`: архив каталога с датой в имени, хранение последних 7 копий, лог
- [ ] Запуск `backup.sh` по systemd timer; проверка через `systemctl list-timers` и `journalctl`
- [ ] `run-on-all.sh '<команда>'`: выполняет команду на всех трёх VM и печатает вывод с именем хоста
- [ ] `pg-backup.sh`: `pg_dump` базы, сжатие, ротация и копия на другую VM через `rsync`

**Готов, когда** бэкап неделю отрабатывает по таймеру без твоего участия, а намеренно вызванный сбой виден в журнале.

## Этап 8. Итоговые проекты

Два-три проекта из списка закрывают roadmap и становятся твоим портфолио на GitHub.

- [ ] **Bootstrap новой VM.** Один скрипт для Debian, Ubuntu и Rocky: обновление пакетов, пользователь с sudo, раскладка SSH-ключа, отключение входа по паролю, базовый набор утилит. Идемпотентный, с `--dry-run`.
- [ ] **Отчёт о состоянии серверов.** Диски, память, load average, упавшие службы, последние неудачные входы. Собирается со всех VM по SSH в один отчёт.
- [ ] **Бэкап с восстановлением.** Развитие `pg-backup.sh`: настройки в отдельном конфиге, проверка дампа пробным восстановлением, парный скрипт `restore.sh`.
- [ ] **Аудит пользователей.** Учётки без пароля, с UID 0, с истёкшим паролем; файлы с SUID вне списка известных.

У каждого проекта: README с примером запуска, чистый `shellcheck` и осмысленная история коммитов.

## Ресурсы и что дальше

Основной учебник на этапы 1–4 — четвёртая часть «The Linux Command Line»; остальное открывается под конкретный вопрос.

| Ресурс | Когда открывать |
| --- | --- |
| [The Linux Command Line](https://linuxcommand.org/tlcl.php), Уильям Шоттс | Часть 4 «Writing Shell Scripts» — основа для этапов 1–4. Бесплатный PDF, есть русское издание |
| [BashGuide](https://mywiki.wooledge.org/BashGuide) | Второй взгляд на те же темы с упором на правильные привычки |
| [BashPitfalls](https://mywiki.wooledge.org/BashPitfalls) | После этапа 2: типичные ошибки и их исправление |
| [BashFAQ](https://mywiki.wooledge.org/BashFAQ) | Когда ищешь, как в Bash сделать что-то конкретное |
| [ShellCheck](https://www.shellcheck.net/) | Постоянно: проверка скрипта и объяснение каждого замечания |
| [explainshell](https://explainshell.com/) | Когда встретил непонятную команду в чужом скрипте |
| [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) | На этапах 4 и 6: как оформлять скрипты |
| `man bash` и `help <команда>` | Точный справочник по синтаксису и встроенным командам |

**Что дальше.** Bash хорош для коротких утилит и склейки команд. Гайд Google советует переписывать на другом языке скрипты длиннее 100 строк или со сложной логикой. Следующие шаги — Python для таких задач и Ansible для настройки многих серверов; оба лежат на пути к DevOps.
